# Windows 最小可分发版设计说明

日期：2026-06-17

## 1. 背景

当前仓库已经具备一套可运行的桌面端开发形态：

- 前端使用 React + Vite
- 桌面壳使用 Tauri
- 本地后端使用 FastAPI

现有桌面端主要面向开发机使用。它可以在启动时拉起本地 Python 后端，并在 Tauri 窗口中加载前端界面。

但这套形态还不能直接作为“给别人安装后即可使用”的 Windows 应用分发，主要原因有：

- 当前桌面壳启动后端依赖本机 Python 环境。
- 当前后端启动逻辑依赖源码仓库目录结构。
- 当前可运行产物位于 `src-tauri/target/release/`，不是正式安装包。
- 当前 API 配置方式更偏开发者环境，而不是普通用户安装后填写配置。

本设计说明的目标，是把当前开发态桌面端推进为一个 `Windows only` 的“最小可分发版”。

## 2. 目标

本次设计的目标是：

- 产出一个可安装的 Windows 桌面应用。
- 用户安装后可以直接打开应用，而不需要自己安装 Python。
- 应用启动时可以自动拉起本地后端。
- 用户在首次使用时，可以通过应用内配置 API key 后体验核心功能。
- 保持当前前端、Tauri 桌面壳和 Python 后端的整体架构，不做大规模重写。

## 3. 非目标

本次不包含以下内容：

- macOS 或 Linux 分发。
- 自动更新。
- 应用签名、证书、商店分发。
- 一步到位的完整商业化安装体验。
- 将 Python 后端改写为 Rust 后端。
- 多用户、云同步、登录体系。
- 完整的首次启动引导流程产品化。

本次目标是“最小可分发版”，不是“完整正式版”。

## 4. 交付定义

完成后应能满足以下交付标准：

- 可以生成一个 Windows 安装包。
- 用户安装后，在开始菜单或桌面快捷方式中打开应用。
- 应用可以正常显示前端界面。
- 应用可以自动启动 bundled backend。
- 即使用户尚未配置 API key，应用也至少可以打开，并展示明确的配置入口。
- 当用户填写最小必需配置后，可以体验导入、摘要、搜索和问答的主流程。

## 5. 推荐方案

推荐方案是：

**保留当前 Python 后端架构，将后端单独打包为 Windows 可执行文件，并随 Tauri 安装包一起分发。**

这意味着分发包中至少包含：

- Tauri 桌面壳
- 前端构建产物
- Python 后端可执行文件
- 后端运行所需的静态资源与默认数据目录

桌面端启动时不再依赖：

- 用户本机 Python
- `python -m backend.app.run`
- 当前源码仓库目录结构

而是改为：

- 由 Tauri 启动 bundled backend executable
- 等待 `/health` 成功后再显示主窗口

## 6. 方案选择理由

之所以采用这个方案，是因为它在当前项目状态下最务实：

- 它不要求推翻现有 FastAPI 后端。
- 它不要求把业务逻辑迁移到 Rust。
- 它可以最大程度复用现有前后端通信方式。
- 它能解决“用户电脑没有 Python 无法使用”的核心分发问题。
- 它比“要求用户自己安装 Python 和依赖”更接近真正可分发的桌面应用。

相比之下：

- 继续依赖用户本机 Python，分发门槛仍然过高。
- 彻底改为 Rust 后端，改动范围远超本次最小可分发目标。

## 7. 架构设计

### 7.1 总体结构

分发后的应用结构保持三层：

1. 前端界面层
2. Tauri 桌面壳
3. 本地后端服务

关系如下：

- 前端负责界面、交互、页面状态和 API 调用。
- Tauri 负责窗口、资源分发、桌面启动流程和后端进程管理。
- 后端负责导入、抓取、摘要、索引、搜索、问答和本地数据读写。

### 7.2 启动流程

目标启动流程如下：

1. 用户打开桌面应用。
2. Tauri 先定位 bundled backend executable。
3. Tauri 为本次会话保留一个本地端口。
4. Tauri 启动 backend executable，并传入运行所需端口和必要环境变量。
5. Tauri 轮询 `/health`。
6. 后端准备完成后，Tauri 再显示主窗口。
7. 主窗口通过注入的 API base URL 访问后端。
8. 应用退出时，Tauri 只清理自己启动的后端进程。

### 7.3 后端定位方式

当前开发态代码通过项目根目录和 Python 模块路径定位后端。

分发态应改为：

- 使用 Tauri 的资源路径或安装目录路径定位 bundled backend executable
- 不再依赖源码根目录存在 `backend/app`
- 不再依赖 `python` 或 `py -3` 命令可用

### 7.4 前端资源加载方式

开发态继续使用现有方式：

- debug 模式加载本地 Vite dev server

分发态使用：

- Tauri bundle 中内置的前端静态资源

这部分沿用现有 release 模式逻辑，不改变前端的主结构。

## 8. 配置设计

### 8.1 配置目标

最小可分发版中，用户应该可以在不修改源码、不手动编辑 `.env` 的前提下完成 API 配置。

### 8.2 最小必需配置

最小版本优先保证一个配置路径可用：

- `SILICONFLOW_API_KEY`

原因：

- 它最容易作为统一入口理解。
- 它可以覆盖聊天、摘要、embedding 和部分 rerank 能力。
- 对普通用户来说，比要求分别配置多个 key 更容易上手。

### 8.3 进阶配置

以下配置保留为进阶项：

- `CHAT_API_KEY`
- `EMBEDDING_API_KEY`
- `RERANK_API_KEY`
- `SILICONFLOW_BASE_URL`
- 其他模型相关 base URL 或模型名配置

这些配置仍可继续支持，但不应阻碍最小版交付。

### 8.4 缺失配置时的行为

如果用户未配置最小 API key：

- 应用仍然可以打开。
- 首页、知识库和设置页应可进入。
- 依赖模型能力的操作应返回清晰错误。
- 文案应明确提示“需要先配置 API 才能使用导入、摘要、搜索或问答能力”。

最小版不要求在首次启动就做复杂引导，但必须让用户知道缺什么、去哪里补。

## 9. 数据与资源布局

### 9.1 打包内容

Windows 安装包中应至少包含：

- 前端静态资源
- Tauri 桌面壳可执行文件
- Python 后端可执行文件
- 后端运行依赖文件
- 默认可写数据目录初始化逻辑

### 9.2 数据目录要求

分发版不能继续默认把运行日志、SQLite 数据和运行时文件写回源码仓库路径。

分发版应改为：

- 使用应用本地数据目录
- 或使用用户目录下的应用专属数据目录

该目录至少要承载：

- 产品库数据
- RAG 数据
- 运行日志
- 运行时配置

### 9.3 日志要求

最小版仍保留启动日志与后端日志，但位置要改为分发版可写目录，而不是源码目录下的 `backend/data/`。

## 10. 安装包设计

### 10.1 打包形式

本次目标是 Windows 可安装产物。

优先采用 Tauri 官方支持的 Windows bundle 产出，例如：

- `msi`
- 或 Tauri 默认支持的 Windows 安装器形式

具体选型可在实现阶段根据当前 Tauri 2 配置能力决定，但目标一定是“用户可以安装”，而不是只给一个裸 `exe`。

### 10.2 用户体验要求

最小版安装体验要求：

- 用户可以完成安装。
- 安装后可以从应用入口打开。
- 不要求用户先打开命令行。
- 不要求用户自己拼接运行参数。
- 不要求用户额外安装 Python。

## 11. 错误处理

最小可分发版需要重点覆盖以下错误：

- bundled backend executable 缺失
- 后端启动失败
- 后端健康检查超时
- 数据目录不可写
- API key 未配置
- 模型调用失败

错误处理要求：

- 应用不能静默失败。
- 应尽量显示可理解的用户提示。
- 至少要保留日志，便于后续排查。

## 12. 测试与验收

### 12.1 核心验收场景

必须覆盖以下场景：

1. 在有完整开发环境的机器上生成安装包成功。
2. 在未安装 Python 的 Windows 机器上安装应用。
3. 应用首次启动成功，主窗口正常打开。
4. 应用能自动启动 bundled backend，并通过 `/health`。
5. 未配置 API key 时，应用可以打开且提示去设置中配置。
6. 配置 `SILICONFLOW_API_KEY` 后，核心 AI 流程可进入可用状态。

### 12.2 回归重点

需要重点回归：

- 开发态 `npm run desktop:dev` 不被破坏
- release 模式前端仍能正确加载
- 后端启动与退出清理逻辑
- 设置页运行时配置保存逻辑

## 13. 实施拆分

建议按以下顺序实施：

### 阶段 1：打包能力准备

- 打开 Tauri 的 Windows bundle 配置
- 确认 release 模式前端资源可正常打进桌面端

### 阶段 2：后端可执行化

- 为 Python 后端增加 Windows 可执行文件打包脚本
- 明确后端打包产物输出位置
- 验证打包后后端可独立启动并通过 `/health`

### 阶段 3：桌面壳启动逻辑改造

- 分发态从 bundled backend executable 启动后端
- 开发态保留当前 Python 启动逻辑，避免影响本地开发
- 调整日志目录和数据目录定位方式

### 阶段 4：配置与用户提示

- 确保设置页能支撑最小 API 配置
- 确保缺失配置时的错误提示对普通用户可理解

### 阶段 5：安装包验证

- 生成 Windows 安装包
- 在尽量干净的 Windows 环境验证安装、启动和配置流程

## 14. 需要修改的文件范围

预期至少涉及以下区域：

- `src-tauri/tauri.conf.json`
- `src-tauri/src/lib.rs`
- `src-tauri/Cargo.toml`
- `backend` 下新增后端打包脚本或打包配置
- 运行时配置相关代码
- README 或面向用户的安装使用文档

实现阶段可以根据实际需要补充，但不应偏离本设计范围。

## 15. 风险与边界

本方案的主要风险有：

- Python 后端打包后，某些依赖可能需要额外资源收集
- 安装包内的数据目录与权限问题可能导致首次运行失败
- 后端路径定位如果和 Tauri 安装目录策略不一致，可能导致启动失败
- API 能力虽然最小可用，但第一次配置体验可能仍然偏技术化

这些风险不改变本次方案方向，但实现阶段必须优先验证。

## 16. 结论

对于当前项目，最合理的 Windows 最小可分发方案是：

- 保留现有前后端架构
- 将 Python 后端打包为可执行文件
- 由 Tauri 在分发态中直接启动 bundled backend
- 使用 Tauri 输出正式 Windows 安装包
- 让用户安装后直接打开应用，并在设置页填写最小 API 配置

这条路线能在最小改动下，把当前开发机桌面端推进到真正可安装、可分发、可试用的 Windows 应用。
